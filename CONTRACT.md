# Lead CRM — data contract

The CRM app (`app/`) and the research robot (`robot/`) meet ONLY here: the Supabase tables below.
Change this file together with any schema migration.

Base: Atomic CRM (marmelab, MIT), copied into `app/`. Its tables stay as they are
(`companies`, `contacts`, `deals`, `tasks`, `contact_notes`, `deal_notes`, `sales`, `tags`,
`configuration`). We ADD columns and tables; we never rename or drop Atomic's.

## 1. One lead = one business

| Atomic record | Our meaning |
|---|---|
| `companies` row | The business. One per lead. Holds research. |
| `deals` row | Its card on the board. Exactly one per company, `name` = company name. |
| `contacts` row | The owner if known (`title='Owner'`), else one contact `first_name='Front desk'` holding the main phone. Every company has ≥1 contact, because Atomic `tasks` hang off `contact_id`. |
| `tasks` row | The **next step**: `text`, `due_date`, `type`. Open = `done_date is null`. |
| `deals.sales_id` | Who owns the lead. |

## 2. Deal stages (`configuration.config.dealStages`, in this order)

| value | label |
|---|---|
| `found` | Found |
| `researched` | Researched |
| `tested` | Tested |
| `contacted` | Contacted |
| `replied` | Replied |
| `call-booked` | Call booked |
| `won` | Won |
| `lost` | Lost |

`deals.category` = `enquiry-service` for all leads (reserved for future lead sets).

## 3. Columns added to `companies`

| column | type | written by | meaning |
|---|---|---|---|
| `external_key` | text UNIQUE | upload + robot | dedupe key: lowercase bare domain (`acme.com`) if website known, else `lower(name)|lower(city)|state` |
| `research_status` | text not null default `'to_research'`, check in (`to_research`,`researching`,`done`,`failed`) | upload → robot | queue flag |
| `research` | jsonb | robot only | see §6 |
| `first_line` | text | robot; user may edit | one sentence, see §7 |
| `score` | smallint | robot | higher = better lead |
| `timezone` | text | upload / robot | IANA, e.g. `America/Chicago` (Dallas), `America/New_York` (Atlanta) |
| `source` | text | upload | where the lead was found, e.g. `indeed:receptionist`, `meta-ads:free quote Dallas` |
| `business_type` | text | upload / robot | e.g. `home services`, `law firm` (Atomic's `sector` is left alone) |

Existing Atomic columns used as-is: `name`, `website`, `phone_number` (E.164, `+1…`), `city`,
`state_abbr`, `country` (`US`), `description` (robot writes a 1–2 line human summary).

## 4. New tables

```sql
-- outside-in checks: contacting the business the way a customer would
create table public.enquiry_tests (
  id bigint generated by default as identity primary key,
  company_id bigint not null references public.companies(id) on delete cascade,
  channel text not null check (channel in ('web_form','phone','email','chat','whatsapp','marketplace','other')),
  what_sent text not null,            -- exactly what we sent / did, as a customer would
  sent_at timestamptz not null,
  replied_at timestamptz,             -- null = no reply yet
  reply_summary text,
  observed text,                      -- facts only, no judgement words
  sales_id bigint references public.sales(id),
  created_at timestamptz not null default now()
);
-- reply time is derived: replied_at - sent_at. Never stored.

create table public.call_logs (
  id bigint generated by default as identity primary key,
  company_id bigint not null references public.companies(id) on delete cascade,
  contact_id bigint references public.contacts(id) on delete set null,
  outcome text not null check (outcome in ('no_answer','voicemail','gatekeeper','spoke_owner','booked','not_interested','wrong_number')),
  note text,
  called_at timestamptz not null default now(),
  sales_id bigint references public.sales(id)
);

create table public.whatsapp_opens (       -- one row each time the WhatsApp button is used
  id bigint generated by default as identity primary key,
  company_id bigint not null references public.companies(id) on delete cascade,
  opened_at timestamptz not null default now(),
  sales_id bigint references public.sales(id)
);
```
RLS on all three: same policy style as Atomic's tables (authenticated users read/write).

## 5. Derived: last touch + red rule (view `deal_health`, security_invoker)

`last_touch_at` = greatest of: `deals.updated_at`, latest `deal_notes.date`, latest
`contact_notes.date` for its contacts, latest `call_logs.called_at`, latest
`whatsapp_opens.opened_at`, latest `enquiry_tests.sent_at`/`replied_at`, latest `tasks.done_date`.

`next_task_due` = earliest `due_date` of open tasks on the company's contacts.

| state | rule (stage not in `won`,`lost`) | shows as |
|---|---|---|
| `overdue` | `next_task_due < now()` | **red** |
| `stale` | `last_touch_at < now() - interval '7 days'` | **red** |
| `no_next_step` | no open task | amber |
| `ok` | otherwise | normal |

Robot writes do NOT count as a touch: the robot never updates `deals.updated_at` except via
the one stage move `found → researched` (the app must treat a deal created <7 days ago as not stale).

## 6. `companies.research` jsonb (robot-owned, version 1)

```json
{
  "version": 1,
  "researched_at": "2026-09-28T10:00:00Z",
  "website":   {"url": "https://acme.com", "match": "exact|likely|none", "fetched": true},
  "chain":     {"is_chain": false, "signal": ""},
  "instant_reply": {"chat_tools": ["gohighlevel"], "booking_tools": [], "has_form": true},
  "owner":     {"name": "Jane Doe", "source_url": "https://…", "confidence": "high|medium|low"},
  "complaints": [{"quote": "never called back", "url": "https://…", "verified_by_human": false}],
  "marketplaces": [{"name": "Angi", "url": "https://…"}],
  "pays_for_enquiries": {"ads": true, "jobs": null, "evidence": ["https://…"]},
  "healthcare": false,
  "score_why": "+2 no chat tool; +1 owner named",
  "facts":    [{"text": "Website has a quote form but no chat or text option", "source": "https://acme.com"}],
  "unknowns": ["owner email"]
}
```
Missing data = key absent or `null`. Never a guess. The app renders this read-only
(a "Research" panel): facts with source links, complaints flagged "unverified" until
`verified_by_human` is true (the app lets a user tick it).

## 7. `first_line` rules
One sentence, ≤ 25 words, works unchanged in an email, a WhatsApp message or spoken on a call.
Built only from `research.facts` (later: from `enquiry_tests.observed`, which beats site facts).
No flattery, no invented numbers, no "I noticed you're a leader in…".

## 8. Who writes what

| Action | Writer | Effect |
|---|---|---|
| Upload a list (CSV: `name`, `city` required; `website`, `phone`, `state`, `business_type`, `source` optional) | App | inserts `companies` (`research_status='to_research'`, `external_key`), one `deals` row (`stage='found'`), one placeholder contact. Duplicate `external_key` → skipped and reported. |
| Research | Robot (local, secret key in `robot/.env`, git-ignored) | picks `research_status='to_research'` → sets `researching` → writes §3/§6/§7 fields, owner contact (renames placeholder or adds), → `done` (or `failed` + `research.error`), moves deal `found → researched`. Touches nothing else. |
| Everything else (stages after researched, notes, tasks, calls, tests, WhatsApp) | App / humans | — |

## 9. Phones
- Business main line → `companies.phone_number` (E.164). Source: the business's own website (robot, free).
- Owner's direct/mobile → owner contact's `phone_jsonb` `[{"number": "+1…", "type": "Mobile"}]`, added by a person.
- Call and WhatsApp buttons prefer the owner's mobile, fall back to the business line, and say which one they use.

Robot is idempotent: re-running on a `done` company only happens with an explicit `--redo`.
